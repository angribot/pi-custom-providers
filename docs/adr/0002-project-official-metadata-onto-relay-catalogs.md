# Project official metadata onto relay catalogs

Relay `/models` endpoints return IDs and nothing usable — no context window, no cost, no reasoning flag — so a relay model built from the response alone is unusable for budgeting and context management. We therefore treat the Catalog as a list of IDs only, and project capability and pricing fields from the `pi-ai` Official Model with the exact same ID, falling back to conservative defaults (128k context, 4k output, zero cost) for IDs we don't recognize.

One field is not projected unconditionally: `compat` is copied only when the Official Model's own API matches the relay's Relay API. Compat quirks describe a wire protocol, so carrying OpenAI's compat block onto a model reached over `anthropic-messages` would describe a request shape that is never sent. Mutable sub-objects (`input`, `compat`, `thinkingLevelMap`) are cloned rather than shared, because the `pi-ai` registry entry is process-wide and a relay's Projection must not edit it.

Prompt cache lifetimes (`promptCache`) are deliberately excluded from Projection. They describe the serving endpoint's cache retention, which a matching model ID and Relay API do not establish for a relay. Pi 0.86 enables cache warming by default when lifetime metadata and its other eligibility checks permit it, so copying official lifetimes could introduce paid refresh requests based on an unverified assumption. Users who know their relay's lifetime can opt in through Pi's `models.json` model overrides; the host applies those after the extension's dynamic models. This keeps warming policy and configuration in Pi.

Consequence: relay models are only as good as `pi-ai`'s builtin catalog, and a `pi-ai` bump can silently change a relay model's advertised limits. Accepted, because the alternative is hand-maintaining per-relay metadata that drifts from the vendor anyway.
